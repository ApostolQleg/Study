# ADR-1788898087: Вибір первинних ключів для сутностей

## Статус
Прийнято

## Контекст
Кожна таблиця у СУБД має мати первинний ключ.
Важливою задачею є вибір їх типів даних. 
Серед поширених варіантів є incremental integer (`BIGSERIAL`), uuid (`UUID`), slug чи власний унікальний код (`TEXT`).
Загалом, у нас є такі сутності як `user`, `anime`, `episode`, `comment`, `room`, `animeListUnit`, `upcomingEpisodes` і кожному з них слід визначити поле, що буде PK.

## Рішення
- Сутностям, що мають окрему сторінку (та посилання на неї) обрати первинний ключ типу UUID з назвою `id`.
    Ці UUID будуть використовуватися для формування посилань на ресурс, тож таке рішення дасть нам наступні переваги:
    * Не можна просто збільшувати/зменшувати (перебирати) числові значення, щоб отримати посилання на інший об'єкт, що є чудовим рішенням для запобігання скрапінгу.
    * Немає прив'язки посилання до порядку створення: в Incremental integer легко дізнатися порядок додавання об'єкту в БД порівнюючи обидва ID.
    * Довіра користувача: якщо ID видно в публічному URL і користувач помічає "діри" (`/anime/47`, `/anime/49`, немає 48) — деякі люди можуть подумати, що це баг чи щось видалили/приховали навмисно (модерація, цензура).
- ID, що заховані за функціоналом Frontend матимуть ключ з типом BIGSERIAL.
    Ось основні моменти:
    * Користувач ніколи не побачить ID коментаря чи серії, що зберігає хороший UX, але також оптимізує сховище БД (оскільки BIGSERIAL займає менше місця ніж UUID).
    * У таких сутностях легко протидіяти скрапінгу, оскільки вони зазвичай знаходяться на сторінці (в контексті) батьківської сутності (як серії та коментарії знаходяться на сторінці аніме).
        Тож щоб запобігти перебору чисел, ми можемо вимагати від системи також ID аніме якому належить коментар/серія.
- Також хотілося б скористатися перевагою читабельних посилань для сторінок аніме та користувача.
    Тож ми використаємо додаткові унікальні поля. Це slug для сутності "anime" та "nickname" для сутності "user".
    Основні моменти:
    * Скрапер все ще не зможе перебирати ID сутностей, так як вони є текстовими типами даних, а не числовими.
    * Як первинний ключ такі поля є неефективними через велику довжину їх значень, але значно покращують UX.
        Тож `slug` та `nickname` доцільно використовувати для посилань, але оперувати UUID на стороні Backend.
    * Ці поля є динамічними (їх можна змінити), тож місце для використання UUID (і для посилань включно, у випадку якщо треба permalink) все ще залишається.
- Сутність `animeListUnit` є асоціативною, тому первинним ключем було обрано пару з `anime_id` та `user_id`.
- Для сутності `upcomingEpisodes` первинним ключем було обрано пару з `anime_id` та `episode_name`.
    Так як одне аніме може мати декілька запланованих епізодів, але лише всі вони мають унікальні назви.
    До відома також варто взяти, що сутність `anime` буде мати окремі об'єкти для різних сезонів одного тайтлу - тож `anime` описує сезони, а не окремі тайтли.
    В іншому ж випадку, якби `anime` описувало весь тайтл, а не сезон, то можливий був би випадок коли серії з різних сезонів мали б однакові назви (сценарій колізії).
- Важливе уточнення щодо версії UUID: оскільки PostgreSQL (наш проєкт орієнтується саме на використання цього СУБД) індексує первинні ключи за допомогою B-Tree, 
    то монотонні первинні ключі значно економлять час та ресурси на обробку вставки об'єкта.
    Керуючись цим нюансом, вибір UUIDv4 є неефективним, оскільки всі біти є хаотичними, тим часом як UUIDv7 у перших бітах записує timestamp (що і робить його приблизно монотонним рішенням).
    Тож всі випадки використання UUID означатимуть використання саме UUIDv7, а не інших версій ідентифікатора.

## Наслідки
У даному ADR ми орієнтувалися на UX та сховище у БД. Вважаємо, що наші рішення якнайкраще вирішують компроміс між цими двома аспектами.

### Плюси

- Безпека проти скрапінгу для публічних сутностей: UUID унеможливлює 
  перебір ID для anime/user; для вкладених сутностей (comment, episode) 
  захист забезпечується контекстною прив'язкою до батьківського anime_id.
- Оптимізоване сховище для сутностей з великим обсягом: BIGSERIAL 
  (8 байт) замість UUID (16 байт) для comment/episode економить місце 
  та пришвидшує вставку завдяки монотонному порядку в B-tree індексах.
- Читабельні посилання без шкоди безпеці: slug/nickname дають 
  зручний UX (`/anime/attack-on-titan` замість `/anime/9f8a...`), 
  залишаючись текстовими (не enumerable), тоді як UUID лишається 
  надійним внутрішнім/постійним ідентифікатором.
- Відсутність проблеми з фрагментацією B-tree індексів: завдяки 
  використанню UUIDv7 (а не UUIDv4) для anime/user, значення 
  зберігають частково монотонний порядок за часом створення 
  (timestamp у перших бітах), тому вставка нових рядків не спричиняє 
  хаотичних page splits, характерних для випадкового UUIDv4.

### Мінуси

- Неоднорідність типів ключів ускладнює побудову єдиного 
  уніфікованого ORM-шару чи спільних абстракцій для всіх сутностей.
- Slug/nickname не є постійними посиланнями — зміна цих полів 
  користувачем "ламає" старі закладки/посилання без додаткової 
  логіки історії/редиректів.

### Компроміси

- Свідомо жертвуємо **уніфікованістю підходу** заради **оптимізації 
  під конкретний профіль навантаження й видимості** кожної сутності — 
  замість одного стандарту "для простоти" по всій БД.
- Постійність посилання (UUID) обрано пріоритетнішою за читабельність 
  там, де це критично (API/backend), а читабельність (slug/nickname) 
  — там, де це критично для UX (публічні URL), з прийняттям ризику 
  "биття" посилань при зміні цих полів.
